# Domain docs

This project uses one `GLOSSARY.md` at the project root and stores architecture decision records in `docs/adr/`.

Before exploring the project, read the glossary and the ADRs relevant to the task when they exist. The `domain-modeling` skill creates these files as terms and decisions are agreed.

Use glossary terms in specs, tickets, refactor proposals, and test names. Bring missing terms to `domain-modeling` when they need a shared definition. If a proposal conflicts with an existing ADR, name the ADR and explain the conflict.
